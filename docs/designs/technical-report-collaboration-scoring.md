## Problem Statement

Benchmark Radar v0.9.0 is a frozen, citable Zenodo report. The next report draft should become more useful by including real cases in which a practitioner or researcher uses Benchmark Radar to make a decision or reach a defensible conclusion.

The current report cannot support a field-wide claim about recent benchmark trends. That is a limit of the available evidence and comparison window, not evidence that no trend exists. The draft should turn that limitation into open research assignments and invite collaborators to complete them through GitHub issues and pull requests. The four initial use cases are examples, not a closed list.

The current report's "Use it" box only asks readers to cite the project. It does not tell them which unanswered questions matter, what evidence to contribute, how work reaches the PDF, or how substantial contributors become coauthors.

## What Makes This Cool

The report becomes a public research program rather than a static description of a pipeline. Every claimed use case must come from work another person actually performed. The path from assignment to evidence, code, analysis, prose, and authorship stays visible in one GitHub issue.

## Constraints

- Freeze the published Zenodo v0.9.0 record. Work only on the next draft; publication and arXiv submission are later steps.
- Do not write invented or illustrative success stories. Until a collaborator completes a case, label it as an open research question.
- Rebuild the data pipeline before changing quantitative report claims. Derived files and the current PDF are not sources of truth.
- Use GitHub issues as the complete unit of assignment and scoring. Do not maintain a second private point system.
- Treat each issue's score label, primary assignee, one or more linked pull requests, and state as canonical. Any master table is a dated, read-only summary of those issues rather than another source of truth.
- Keep code and report commits explicit. The contributor workflow may assign or unassign issues, post deadline comments, and commit only the generated `docs/contributor-points.md` ledger when scores change; it never commits code or merges report changes.
- Authorship still requires substantial contribution, manuscript drafting or critical revision, final approval, and accountability for the work.

## Premises

- "No certified trend" means the current corpus cannot justify the conclusion; it does not mean the underlying field has no trend.
- A real use case records the user's question, the Radar data or interface used, the analysis performed, the decision or finding, and limitations.
- Any issue whose title begins with `[N points]` is part of the public contribution program, regardless of label. Existing `friends` issues are the first scored set, not the boundary of the program.
- A contributor may propose any real Benchmark Radar use case. An accepted use-case issue starts at three points and may be rescoped before assignment.
- One issue has one primary assignee and one score. If two people need independently countable work, split the issue before assignment.
- Issue points are earned only when the required linked pull requests are merged and the issue's acceptance criteria are satisfied.
- A rigorous finding that the available evidence is insufficient is a valid result for UC3 or UC4 when the inclusion rules, comparison protocol, and missing evidence are documented.
- Once a contributor has at least one accepted report-used analysis or subsection and completes the manuscript obligations, all of their earned issue points count toward author ordering.
- Historical merged pull requests from every author other than `ktwu01` receive retroactive points. Bot work is recorded but cannot occupy a human collaborator or author seat.

## Approaches Considered

- **Approach A: One score per issue. Chosen.** Completed issue scores add up, and collaborator byline order follows the totals.
- **Approach B: CRediT roles without points. Rejected.** It records contribution types but does not give collaborators a visible work queue or ordering rule.
- **Approach C: Separate task and paper scores. Rejected.** The user considers the extra ledger unnecessary; the issue is the unit of work and credit.

## Recommended Approach

### 1. Add a report section that asks for completed cases

Place a new subsection after "6.4 What to build next" and before the current "Use it" callout.

Proposed reader-facing copy:

> **Call for real Benchmark Radar use cases / 征集真实 Benchmark Radar 使用案例**
>
> The current evidence does not yet support a reliable conclusion about recent field-wide benchmark trends. We are looking for collaborators who can use Benchmark Radar to answer one of the real questions below, document the full method, and help write or revise the resulting report section.
>
> 1. **Evaluation selection for an industry agent.** I am an agent engineer choosing an evaluation system. Which benchmarks should my agent use, and how should I monitor new benchmark releases?
> 2. **Prior-art research for a new benchmark paper.** I am designing a benchmark. What have other benchmark authors measured, where do their protocols differ, and which gap is still real?
> 3. **LLM development through benchmark scores.** What development pattern can be supported by protocol-aware score observations, and where do changed prompts, tools, attempts, or evaluators prevent comparison?
> 4. **Agent development and weaknesses.** Which agent capabilities or failure modes recur across benchmarks, and what evidence supports that conclusion?
>
> These are starting examples, not limits. Contributors may propose any real use case as a three-point issue. Each study runs through a scored GitHub issue and pull-request discussion. Accepted evidence, analysis, and prose will be merged into the next report source and rebuilt PDF. Contributors whose completed issue work is substantial and who participate in manuscript drafting or critical revision, final approval, and accountability will be invited as coauthors.

The final arXiv/Zenodo report should contain completed findings, not invitations alone. Until then, the draft must show unfinished work as open studies.

### 2. Make real use cases three-point issues

The four starting cases and any contributor-proposed real use case are worth three points. A use case is a documented application of Benchmark Radar, not a testimonial. It can later be split or rescored before assignment if the accepted scope is materially larger or smaller.

Every case-study issue must require:

- a concrete user and decision or research question;
- reproducible Radar queries, pages, exports, or source records;
- the alternatives or comparison set considered;
- a result with cited evidence;
- limitations and counter-evidence;
- a pull request that adds or revises the relevant manuscript text;
- final review of the integrated report section.

The minimum reproducibility package attached to the issue or pull request is:

- exact Benchmark Radar page, query, CLI command, or exported record identifiers;
- snapshot date, generated-data version, and repository commit;
- inclusion and exclusion rules decided before interpreting the result;
- input records and an analysis artifact, such as a table, notebook, script, or checked calculation;
- citations or source URLs for every external claim;
- enough environment and command information for a reviewer to repeat the analysis;
- a limitations section that names protocol mismatches, missing observations, and plausible counter-readings.

The four expected outputs are:

| Track | Report-ready output | Score |
|---|---|---:|
| UC1: industry agent evaluation | A selection memo comparing candidate evaluation systems and explaining the chosen suite | 3 |
| UC2: new benchmark paper | A prior-art map showing related benchmarks, protocol choices, duplication risks, and the remaining gap | 3 |
| UC3: LLM development | A protocol-aware score analysis that separates comparable movement from changed evaluation settings | 3 |
| UC4: agent development | An evidence-backed taxonomy of recurring agent capabilities, weaknesses, and measurement gaps | 3 |

Track-specific acceptance checks:

- **UC1:** name a real agent workflow and its failure cost; identify at least three candidate evaluation systems through reproducible Radar searches; compare task fit, protocol, maintenance, and evidence coverage; record the chosen suite and rejected alternatives.
- **UC2:** state the proposed benchmark construct; identify the closest prior benchmarks from both the daily-discovery and external-catalog layers; compare task, data, metric, protocol, and contamination or duplication risks; state the remaining gap or conclude that the proposed benchmark is not sufficiently distinct.
- **UC3:** predeclare the benchmark and comparison window; retain only observations with compatible protocols or show protocol strata separately; identify changed prompts, tools, attempts, budgets, or evaluators; cite and evaluate the authoritative `comparable_window` and measurement-conflict gates in `src/benchmark_radar/findings.py`; report a trend only if the rebuilt data passes those gates, otherwise report why no trend is certified.
- **UC4:** predeclare the agent capability scope and benchmark inclusion rule; code cited tasks or failure evidence into a reviewable taxonomy; publish a coding guide; have a second reviewer independently code a sample and adjudicate every disagreement; test alternative groupings and counterexamples; separate weaknesses demonstrated by benchmark evidence from weaknesses merely suggested by benchmark design.

### 3. Score any eligible repository issue on one public scale

Put a positive-integer score at the start of the title, such as `[2 points]` or `[12 points]`. There is no five-point ceiling. Only prefixed issues are claimable. An unscored issue may be proposed for the program, but its score must be fixed before anyone claims it.

| Score | Meaning |
|---:|---|
| 1 | Tiny, bounded copy, documentation, or outreach improvement |
| 2+ | Bug fix or other small tested implementation; bugs are never scored below 2 |
| 3 | A new, accepted real use case; also suitable for a validated catalog addition or focused analysis |
| 4–11 | Increasingly broad engineering, data, or report work, scored from explicit acceptance criteria |
| 12 | Complex UI work, including the current UI comparison and implementation issues |

Assign the score from the complete accepted scope before a contributor claims the issue. The score reflects completion difficulty, review burden, and required evidence—not the number of files changed. The lead author resolves boundary cases publicly before assignment. Contributor-proposed use cases default to three points; bugs have a floor of two points; the current UI issues are twelve points because they require complex product judgment, implementation, and validation.

The lead author or a named reviewer owns the independent reproduction step. If reproduction itself requires substantial new work, create and score a separate validation issue before it begins; the original issue keeps its indivisible score, and the validation issue credits the reviewer independently.

Boundary examples: a one-line copy correction may be 1; a bounded bug fix begins at 2; a contributor-proposed real use case is 3; a connector plus coverage analysis and manuscript findings may be 4 or more; complex UI work is 12. Larger work may exceed 12 when its published acceptance criteria justify it.

### 4. Make assignment and point accounting deterministic

Each scored issue follows one lifecycle:

| State | Required evidence | Point effect |
|---|---|---|
| Proposed | Draft scope; no score or assignee yet | None |
| Ready | Acceptance criteria and one score label are present | Available to claim |
| Assigned | A contributor comments `/claim`; automation assigns that commenter as the only assignee and records a seven-day deadline | Reserved, not earned |
| In review | One or more linked pull requests address the acceptance criteria | Reserved, not earned |
| Complete | Required pull requests are merged and the issue closes as completed no more than seven days after assignment | Score earned once |
| Expired | Seven days pass without qualifying completion; automation removes the assignee and comments with the expired deadline | No points; returns to Ready |
| Unassigned | Assignee withdraws before the deadline; maintainer or automation removes assignment publicly | No points; returns to Ready |
| Closed without completion | Duplicate, declined, superseded, or closed as not planned | No points |

- Duplicate or competing work earns no points unless it was split into a separately scored child issue before implementation.
- If several people need credit, split their independent deliverables into child issues before work begins. Review alone is recorded in CRediT or acknowledgements and does not divide the primary issue's score.
- Multiple pull requests may satisfy one issue, but its score is awarded once to the primary assignee after the final required merge.
- Reopening a completed issue does not award the score again. New independently creditable scope requires a new issue.
- If scope must change after assignment, pause work and record the new acceptance criteria and score in a public comment approved by the maintainer and assignee before more work proceeds.
- Before work resumes after a rescope, update the canonical score label, acceptance checklist, assignee, and expected pull-request links together; the closing record must reference the approved rescope comment.
- Contributors may complete multiple issues; their scores add together.
- Do not award discretionary bonus points. If work is larger than the issue, open another scored issue.
- Ordinary public visitors cannot assign issues directly under GitHub's permission model. The `/claim` workflow performs the assignment using repository issue-write permission after verifying that the issue is scored and unassigned.
- An assignment event starts a strict 168-hour window. Completing work after that timestamp earns no points from the expired claim; the contributor may claim the issue again only after it returns to Ready.

Canonical issue metadata:

- one positive-integer `[N points]` title prefix;
- one primary GitHub assignee;
- a checklist of acceptance criteria;
- linked pull requests using GitHub's closing keywords or explicit links;
- a closing comment naming the merged pull requests, report section affected, and earned score.

The contributor-points calculator reads title prefixes, assignment events, issue completion state, closing pull requests, and historical prefixed pull requests. It prints a dated JSON or Markdown report containing earned points, active and expired claims, totals, and the six-point collaborator threshold. Issue and pull-request metadata remain canonical; generated totals are disposable.

### 5. Use totals for collaborator author order

- Koutian Wu remains lead and corresponding author for the system conception, implementation, original analysis, and v0.9.0 manuscript.
- A new contributor receives a collaborator seat after earning at least **6 points**. Coauthorship additionally requires at least one completed issue supplying original analysis used in the report or an accepted method/result/limitations subsection, participation in drafting or critical revision, final manuscript approval, and accountability.
- Eligible collaborators are listed after the lead author in descending order of completed issue points.
- Equal totals receive an equal-contribution statement when the work is comparable; names within that tied group are alphabetical.
- If equal totals do not represent comparable contributions, names are still alphabetical within the tied score group; equal-contribution language is a separate editorial decision.
- The final manuscript includes a CRediT contribution statement describing what each author did. CRediT documents the work; issue points determine the ordering rule.
- Contributors below the byline threshold receive named acknowledgement, with permission, and remain visible through their issues and merged pull requests.

The lead author validates issue completion and the initial byline calculation in public comments. A contributor may appeal within seven calendar days in the master issue, citing the canonical issue metadata. All current eligible authors review the appeal and publish the resolution; before another author is eligible, the lead author's documented resolution controls.

Before submission, each candidate supplies their preferred name, affiliation, optional ORCID, CRediT roles, conflict disclosures, and written approval. Candidates receive seven calendar days for manuscript review, one reminder, and a final seven-day extension. Anyone who declines accountability, requests withdrawal, or does not approve after the extension moves to acknowledgement if they consent; the remaining eligible authors recalculate the byline from unchanged issue totals.

### 6. Set a cutoff instead of moving the goalposts

The master issue must publish an assignment cutoff and a contribution cutoff for the target report draft. Score totals freeze at the contribution cutoff. Work merged afterward counts toward a later version rather than changing author order during final review.

Only future issue work uses the seven-day assignment rule. Every historical merged pull request whose author is not `ktwu01` receives a fixed retroactive score and counts once. Automation accounts may accumulate recorded points but are excluded from human collaborator and author eligibility.

### 7. Separate completed findings from open work in the report

- A completed use case appears in the findings section with its method, evidence, result, limitations, contributor, and issue link.
- An active study appears only in the future-work collaboration box with assignee, score, and issue link. It contributes no finding yet.
- An unclaimed study appears only in that collaboration box as available work. Readers may also add a different real use case through the three-point issue form.
- If no studies are complete, the next draft contains the collaboration box but makes no use-case result claim.
- The arXiv/Zenodo release contains completed findings plus a short future-work box for any remaining studies. It never presents an active or unclaimed study as evidence.

## Success Criteria

- The draft distinguishes "no supported trend conclusion" from "no trend exists."
- The report presents the four starting use cases as examples and explicitly accepts other real use cases.
- Each use-case issue has a primary owner, score, reproducible deliverables, and report-writing requirement.
- Every claimable issue has a positive-integer point prefix, exactly one assignee, and acceptance criteria before assignment; bugs are at least two points, new use cases are three, and complex UI issues are twelve.
- A `/claim` workflow assigns external commenters, rejects occupied or unscored issues, and removes expired assignees after seven days.
- The calculator awards issue points only for a qualifying completion inside 168 hours, counts every prefixed historical non-owner PR once, and shows the six-point collaborator threshold.
- The use-case issue form accepts contributor-defined cases and starts their titles at three points.
- Authorship eligibility, collaborator ordering, tie handling, acknowledgements, and the contribution cutoff are published before work begins.
- The eventual report includes only completed cases with evidence and limitations; unfinished cases remain labeled as open work.
- Each coauthor reviews and approves the final manuscript and has a visible CRediT contribution statement.
